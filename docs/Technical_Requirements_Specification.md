# 📋 Спецификация технических требований (Technical Requirements Specification)

Этот документ описывает перечень функциональных и нефункциональных требований к системе **Kawaii Neuro Maid (KNM)**. Все требования обязательны к выполнению в рамках разработки MVP.

---

## 1. Функциональные требования (Functional Requirements)

### 1.1. Сбор и агрегация данных (FR-ETL)
*   **FR-ETL-1:** Система должна асинхронно принимать события изменения состояния физических датчиков по сетевому протоколу.
*   **FR-ETL-2:** Система должна сохранять все входящие события в локальную реляционную базу данных с фиксацией точного времени и уникального идентификатора датчика.
*   **FR-ETL-3:** Система должна выполнять квантование временных рядов, разбивая сутки на регулярные 5-минутные интервалы.
*   **FR-ETL-4:** Система должна преобразовывать асинхронные логи событий в структурированные числовые матрицы активности, где строки — это временные интервалы, а столбцы — состояния датчиков (0 или 1).

### 1.2. Математический анализ среды (FR-CHAOS)
*   **FR-CHAOS-1:** Система должна вычислять показатель Ляпунова ($\lambda$) по скользящему временному окну для оценки текущей предсказуемости поведения среды.
*   **FR-CHAOS-2:** Расчет показателя Ляпунова должен производиться в изолированном программном модуле, не зависящем от структуры базы данных и сетевых протоколов.

### 1.3. Прогнозирование и адаптивное управление (FR-PRED)
*   **FR-PRED-1:** Система должна прогнозировать вероятность наступления целевых событий автоматизации на временной горизонт в 15 минут вперед.
*   **FR-PRED-2:** Система должна динамически рассчитывать порог принятия решений (порог срабатывания) как функцию от показателя хаоса: $Threshold = f(\lambda)$.
*   **FR-PRED-3:** Система должна блокировать автоматическую отправку управляющих команд в шину MQTT, если расчетная вероятность прогноза ниже динамического порога безопасности.

### 1.4. Пользовательский интерфейс и обратная связь (FR-UI)
*   **FR-UI-1:** Система должна отправлять мгновенные текстовые уведомления пользователю через Telegram-бот при автоматическом выполнении сценариев.
*   **FR-UI-2:** Система должна предоставлять пользователю интерактивные элементы управления (кнопки одобрения/отмены `👍/👎`) в окне чата Telegram-бота.
*   **FR-UI-3:** При нажатии пользователем кнопки отмены (`👎`), система должна немедленно отправить команду отключения прибора в шину MQTT и наложить временную локальную блокировку (2 часа) на автоматический повтор этого сценария.
*   **FR-UI-4:** Система должна записывать факт и время каждого пользовательского одобрения или отмены (`👍/👎`) в базу данных для последующего фонового обучения.

### 1.5. Безопасность и аппаратная защита (FR-SAFE)
*   **FR-SAFE-1:** Система должна реализовывать жесткие логические правила безопасности (Guardrails), перекрывающие любые команды от нейросетевого ядра.
*   **FR-SAFE-2:** Система должна аппаратно отключать реле нагрузки при превышении лимита непрерывного времени работы.
*   **FR-SAFE-3:** Система должна мгновенно обесточивать розетку прибора, если датчик энергопотребления фиксирует нулевой ток нагрузки при поданном напряжении.

### 1.6. Эволюционная оптимизация (FR-OPT)
*   **FR-OPT-1:** Система должна в фоновом режиме по расписанию проводить оптимизацию структуры и весов нейросети методом генетического алгоритма.
*   **FR-OPT-2:** Функция приспособленности генетического алгоритма должна штрафовать модели на основе накопленной в БД истории пользовательских отказов (`👎`).

### 1.7. Web-интерфейс администрирования и мониторинга (FR-WEB)
*   **FR-WEB-1:** Система должна предоставлять адаптивный Web-интерфейс (Dashboard) для визуализации состояния умного дома, доступный через стандартные веб-браузеры.
*   **FR-WEB-2:** Web-интерфейс должен в реальном времени отображать текущий статус всех сенсорных и исполнительных узлов системы (состояния "Вкл/Выкл", "Открыто/Закрыто").
*   **FR-WEB-3:** Web-интерфейс должен содержать графический аналитический модуль (графики/диаграммы) для визуализации:
    *   Исторического изменения показателя хаоса Ляпунова ($\lambda$) во времени.
    *   Текущей расчетной вероятности предиктора по целевым сценариям.
*   **FR-WEB-4:** Web-интерфейс должен предоставлять администратору возможность ручного принудительного переключения состояний актуаторов (ручное управление в обход ИИ).
*   **FR-WEB-5:** Web-интерфейс должен содержать модуль просмотра системных логов и сырых событий из базы данных SQLite с возможностью фильтрации по дате и ID устройства.

### 1.8. Безопасность и защита персональных данных (FR-SEC)
*   **FR-SEC-1:** Все собираемые логи активности пользователя должны храниться **строго локально** в энергонезависимой памяти шлюза, без передачи персональной информации на внешние облачные серверы.
*   **FR-SEC-2:** Накопленные в базе данных логи активности должны быть деперсонализированы: записи не должны содержать персональных данных пользователя, а только абстрактные идентификаторы устройств и временные метки.
*   **FR-SEC-3:** Доступ к Web-интерфейсу администрирования должен быть защищен механизмом авторизации (логин/пароль) для предотвращения несанкционированного доступа третьих лиц в локальной сети.
*   **FR-SEC-4:** Все сетевые транзакции между компонентами системы должны быть зашифрованы с использованием стандартных криптографических протоколов (HTTPS / TLS для MQTT), если это поддерживает аппаратная платформа.

### 1.9. Интеграционные требования и внешние интерфейсы (FR-INT)
*   **FR-INT-1:** Web-интерфейс бэкенда должен автоматически генерировать и экспортировать спецификацию API в стандарте **OpenAPI 3.0 (файл `openapi.json`)** для обеспечения интеграции с внешними большими языковыми моделями (LLM) через механизм вызова функций (*Function Calling / Tools*).
*   **FR-INT-2:** Система должна поддерживать стандарт **Home Assistant MQTT Discovery**, публикуя конфигурационные паспорта своих состояний и показателей хаоса в соответствующие топики для автоматической интеграции с внешними голосовыми ассистентами (Яндекс Алиса, Apple HomeKit / Siri, Google Assistant).

## 2. Нефункциональные требования и требования к разработке (NFR-DEV)

*   **NFR-DEV-1 (Эмуляция сенсоров):** Кодовая база должна содержать автономный модуль-эмулятор (`src/utils/mock_sensors.py`), имитирующий отправку сырых MQTT-сигналов активности датчиков по расписанию, для возможности сквозного тестирования системы без наличия физического оборудования.
*   **NFR-DEV-2 (Контейнеризация и деплой):** Все сервисы системы (SQLite, FastAPI, Mosquitto Broker, Predictor Core) должны быть контейнеризированы с помощью **Docker** и управляться единым конфигурационным файлом **`docker-compose.yml`** для обеспечения кроссплатформенного развертывания в одно касание.
*   **NFR-DEV-3 (Логирование и диагностика):** Все системные процессы, асинхронные события, предупреждения и критические ошибки должны записываться в локальный файл логов с использованием стандартной библиотеки Питона `logging` и разделением по уровням важности (`INFO`, `WARNING`, `ERROR`).
*   **NFR-DEV-4 (Автоматизированное тестирование):** Ключевые математические и инфраструктурные модули системы (расчет показателей Ляпунова, парсинг данных, операции с БД) должны быть покрыты юнит- и интеграционными автотестами.
